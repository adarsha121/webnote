    🎛️ systemd, systemctl & journalctl: The "Just Paste It and It Works" Page

    Be honest. You've done this:

    sudo systemctl daemon-reload
sudo systemctl enable --now something
sudo systemctl restart something
journalctl -xeu something

    ...copied from a blog or a forum, and it worked. You moved on. You have no idea what daemon-reload reloads, why enable and start are two different things, or what those -xeu letters mean.

    That's completely normal, and it's exactly what this page is for. We're not going to memorise commands. We're going to build one mental model, and after that every command will feel obvious, like you could have invented it yourself.

    ☕ Coffee again. This is the one where things click.

    1. 🤔 Why do we even need this? (the problem)

    Your computer runs lots of programs in the background, without any window: the web server, SSH, the network manager, Bluetooth, printing, the clock-sync service, and so on.

    These background programs are called services or daemons.

    😈 Fun fact: The word daemon was coined at MIT in the 1960s, named after Maxwell's demon, a thought-experiment creature that quietly sorts things behind the scenes. That's why daemons often end in d: sshd, httpd, systemd, cupsd. (The BSD operating systems even have a little red devil as their mascot, a pun on the same word.)

    Now somebody has to manage them:

    • Start them at boot, in the right order.
    • Restart them if they crash.
    • Stop them cleanly at shutdown.
    • Keep their logs somewhere sensible.

    Without a manager, you'd be the manager, manually launching programs every time you start your computer. 😩

    That manager is systemd. It's the first process started by the kernel (PID 1, as we saw on the boot page), and it becomes the parent of everything else.

    A little history

    Before systemd, services were started by shell scripts in /etc/init.d/, one after another, like a queue at a ticket counter. It worked, but it was slow and each script was written differently. systemd (started by Lennart Poettering and Kay Sievers around 2010) replaced scripts with simple declarative config files and starts things in parallel. Ubuntu adopted it in 2015.

    🗣️ It's also famously controversial: some people feel it does too much for a Unix tool, which goes against the "do one thing well" philosophy from the history page. Whatever your opinion, nearly every major distro uses it, so you need to know it.

    2. 🏢 The mental model: one building, one manager

    Hold on to this picture. Every command on this page maps onto it.

    In the building In Linux
    🧑‍💼 The building manager systemd (PID 1)
    📄 A job description for each staff member A unit file (nginx.service)
    👷 A staff member actually working A running service
    📻 Your walkie-talkie to the manager systemctl
    📹 The CCTV and incident logbook journalctl (reads logs collected by systemd-journald)
    🌗 The building's modes ("night mode", "business hours") Targets (multi-user.target, graphical.target)
    ⏰ The manager's scheduled tasks Timers
    ⏱️ A stopwatch on opening morning systemd-analyze

    So when you type:

    sudo systemctl restart nginx

    ...you're saying into the walkie-talkie: "Manager, please restart the nginx worker." That's it. That's the entire thing.

    3. 🧩 Units: the things systemd manages

    systemd doesn't just manage "services". It manages units, and a service is only one kind. The type is shown by the file extension:

    Unit type Extension What it represents Example
    Service .service A background program ssh.service, nginx.service
    Target .target A group of units / a system state graphical.target
    Timer .timer A schedule that triggers a unit apt-daily.timer
    Socket .socket A network/IPC socket that can start a service on demand docker.socket
    Mount .mount A mounted filesystem home.mount
    Path .path Watches a file or folder and triggers something my-watch.path
    Device .device A hardware device known to the kernel dev-sda1.device
    Slice / Scope .slice, .scope Resource-control groups user.slice

    If you leave the extension off, systemctl assumes .service. So systemctl status nginx means systemctl status nginx.service.

    💡 Ubuntu gotcha: the SSH service is called ssh, not sshd. (Many other distros use sshd. On Ubuntu sshd usually works too, as an alias.)

    4. 📂 Where unit files live

    A unit file is just a small text file. They live in a few places, and the order matters:

    Location Who puts files here Priority
    /etc/systemd/system/ You (the admin) 🥇 Highest. Wins every time
    /run/systemd/system/ Runtime-generated, gone after reboot 🥈 Middle
    /usr/lib/systemd/system/ Packages (apt, snap...) 🥉 Lowest

    (/lib/systemd/system/ points to the same place as /usr/lib/systemd/system/, thanks to the usr-merge story from the file system page.)

    🧠 The rule that saves you

    Never edit files in /usr/lib/systemd/system/. A package update will overwrite your changes. Put your own files or overrides in /etc/systemd/system/. It's like writing notes in your own notebook rather than in the library's reference book.

    Want to see which file a service actually uses?

    systemctl cat nginx

    This prints the unit file and any overrides, in order. A great habit.

    5. 📻 systemctl: your walkie-talkie to the manager

    Every systemctl command follows one pattern:

    systemctl  <VERB>  <UNIT>
              │       └── which staff member? (nginx, ssh, cron...)
              └────────── what should happen?

    Once you see the pattern, you can read any command.

    The verbs you'll use 95% of the time

    Command Plain-English meaning
    systemctl status nginx "How's nginx doing?" (no sudo needed)
    sudo systemctl start nginx "Start nginx now."
    sudo systemctl stop nginx "Stop nginx now."
    sudo systemctl restart nginx "Stop it, then start it again."
    sudo systemctl reload nginx "Re-read your config without dropping connections" (if the service supports it)
    sudo systemctl enable nginx "Start it automatically at every boot."
    sudo systemctl disable nginx "Stop starting it automatically at boot."
    systemctl is-active nginx Prints active or inactive (great in scripts)
    systemctl is-enabled nginx Prints enabled or disabled

    🔄 restart vs reload

    • restart = switch it off and on. Active connections are dropped. Always works.
    • reload = "re-read your config file" while it keeps running. Gentler, but only works if the service knows how to do that.
    • reload-or-restart = try the gentle one, fall back to the blunt one.

    Looking around

    systemctl list-units --type=service          # what's loaded and running right now
systemctl list-units --failed                # what's broken?  (a handy first check!)
systemctl list-unit-files --type=service     # every service installed, and its enabled/disabled state
systemctl list-dependencies nginx            # what does nginx depend on?

    Power controls are systemctl too

    systemctl reboot
systemctl poweroff
systemctl suspend

    🔒 The sneaky one: mask

    sudo systemctl mask bluetooth      # can't be started, even manually or by another service
sudo systemctl unmask bluetooth

    disable says "don't start at boot." mask says "never start. Not by anyone, not by anything." It works by pointing the unit at /dev/null, so it's a "DO NOT DISTURB" sign taped over the door.

    6. 💡 start vs enable: the #1 confusion, solved

    This is the thing almost everyone is confused about, and it's actually very simple.

    🔦 start = flip the light switch ON right now. 🌅 enable = set the light to switch on automatically every evening (every boot).

    These are two independent things:

    Not enabled (won't start at boot) Enabled (starts at boot)
    Not running now Off today, off tomorrow Off right now, will start at next boot
    Running now On today, gone after reboot On today and on every boot

    So:

    • start only: works today, forgotten after reboot. 😬
    • enable only: does nothing right now, but runs from the next boot onwards.
    • You usually want both, and systemd gives you a shortcut:
    sudo systemctl enable --now nginx      # enable + start
sudo systemctl disable --now nginx     # disable + stop

    🎯 What does "enable" actually do?

    Here's the part that makes it click. enable doesn't do anything magical. It just creates a symlink (shortcut):

    sudo systemctl enable nginx
# Created symlink /etc/systemd/system/multi-user.target.wants/nginx.service
#   → /usr/lib/systemd/system/nginx.service

    At boot, when systemd reaches multi-user.target, it looks in the folder multi-user.target.wants/, sees nginx.service in there, and says, "Oh, that needs to start."

    So: - enable = put a shortcut in the "to-do at boot" folder. - disable = remove that shortcut.

    That's all. You can even look at it:

    ls /etc/systemd/system/multi-user.target.wants/

    7. 🩺 Reading systemctl status like a pro

    Most people glance at it and look for the colour green. Let's read it properly:

    ● nginx.service - A high performance web server and a reverse proxy server
     Loaded: loaded (/usr/lib/systemd/system/nginx.service; enabled; preset: enabled)
     Active: active (running) since Sun 2026-10-18 09:12:41 +0545; 2h 14min ago
       Docs: man:nginx(8)
   Main PID: 1523 (nginx)
      Tasks: 3 (limit: 4547)
     Memory: 5.2M
        CPU: 38ms
     CGroup: /system.slice/nginx.service
             ├─1523 "nginx: master process /usr/sbin/nginx"
             └─1524 "nginx: worker process"

Oct 18 09:12:41 mypc systemd[1]: Starting nginx.service ...
Oct 18 09:12:41 mypc systemd[1]: Started nginx.service ...

    Line by line:

    Part Meaning
    ● green Running happily. (⚪ = inactive, 🔴 = failed)
    Loaded: loaded (…; enabled; preset: enabled) The file was found at that path. enabled = starts at boot. preset = the distro's default
    Active: active (running) It's alive. Other states below ⬇️
    Main PID The process ID of the main process
    Tasks / Memory / CPU Resource usage
    CGroup The process family. systemd tracks every child, so stop really kills everything
    Bottom lines The last few log lines from this service (straight from the journal)

    The Active: states you'll meet

    State Meaning
    active (running) Working
    active (exited) Ran once and finished successfully (normal for one-shot tasks)
    inactive (dead) Not running (stopped, or never started)
    activating Starting up (or auto-restarting)
    failed Crashed or exited with an error. Look at the logs!

    8. 🛠️ Build your own service in 5 minutes

    The best way to understand services is to make one. We'll create a silly service that says hello every 5 seconds.

    Step 1: The program

    sudo nano /usr/local/bin/hello.sh

    #!/bin/bash
while true; do
  echo "Hello from my first service at $(date)"
  sleep 5
done

    sudo chmod +x /usr/local/bin/hello.sh

    (/usr/local/bin is where hand-made programs belong, as the file system page explained.)

    Step 2: The unit file (the "job description")

    sudo nano /etc/systemd/system/hello.service

    [Unit]
Description=My first hello service
After=network.target

[Service]
ExecStart=/usr/local/bin/hello.sh
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target

    Understanding every line

    A unit file has three sections, each answering one question:

    Section Question it answers
    [Unit] What is this? And how does it relate to others?
    [Service] How do I run it?
    [Install] When should it start? (used by enable)
    Line Meaning
    Description= A human-friendly label shown in status
    After=network.target "Start me after the network is up"
    ExecStart= The command to run. Always use the full path
    Restart=on-failure "If I crash, restart me"
    RestartSec=3 "Wait 3 seconds before restarting"
    WantedBy=multi-user.target "When the system reaches multi-user mode, start me." That's the symlink target from earlier!

    Step 3: Tell systemd and launch

    sudo systemctl daemon-reload          # "Manager, I added a new job description. Please re-read the folder."
sudo systemctl enable --now hello     # enable at boot + start now
systemctl status hello                # check on it

    Step 4: Watch its output, with no log files needed

    journalctl -u hello -f

    Oct 18 10:30:01 mypc hello.sh[2210]: Hello from my first service at Sun Oct 18 10:30:01 +0545 2026
Oct 18 10:30:06 mypc hello.sh[2210]: Hello from my first service at Sun Oct 18 10:30:06 +0545 2026

    ✨ Click moment: your script just echo'd to its normal output, and systemd automatically captured it into the journal, labelled and timestamped. You never created a log file.

    Step 5: Watch it self-heal 🩹

    sudo pkill -9 -f hello.sh      # violently kill it
systemctl status hello         # it's already back, with a new PID!

    (We used -9 on purpose. A polite kill, which exits cleanly, doesn't count as a "failure", so Restart=on-failure would leave it dead. Use Restart=always if you want it back no matter what.)

    Step 6: Clean up

    sudo systemctl disable --now hello
sudo rm /etc/systemd/system/hello.service
sudo systemctl daemon-reload

    You just wrote, installed, debugged, and removed a real service. 🎉

    A note on Type=

    By default systemd assumes your program stays running in the foreground (Type=simple). Other common types:

    Type When to use
    simple (default) Program runs continuously and doesn't fork into the background
    oneshot Does a task and exits (backups, setup scripts). Pair with RemainAfterExit=yes if you want it to show as "active" afterward
    forking Old-school daemons that fork into the background by themselves
    notify The program tells systemd when it's actually ready

    Other useful [Service] lines: User= (run as this user, not root), WorkingDirectory=, Environment=, ExecStop=, ExecReload=.

    9. 🔁 Why daemon-reload exists

    This confuses everyone, so let's solve it for good.

    systemd reads all unit files once and keeps them in memory (it's the manager with the filing cabinet in their head). If you add or edit a unit file on disk, the manager doesn't know. His memory is out of date.

    📣 daemon-reload = "Manager, I changed the paperwork. Please re-read the folder."

    Important details:

    • It re-reads unit files. It does not restart your services.
    • After editing a unit file, you usually need both: daemon-reload (so he knows the new rules) and restart (so the running service actually uses them).
    • Forgot it? systemd even warns you: "Warning: The unit file ... changed on disk. Run 'systemctl daemon-reload' to reload units." Now you know exactly what that means.
    sudo nano /etc/systemd/system/hello.service     # edit the file
sudo systemctl daemon-reload                    # manager: re-read paperwork
sudo systemctl restart hello                    # service: apply the new rules

    10. 🩹 Changing a service without breaking it (drop-ins)

    Want to tweak a service that came from a package (say, make nginx always restart)? Don't edit the original, because updates will overwrite it. Use a drop-in override:

    sudo systemctl edit nginx

    This opens an empty editor. Type only what you want to change:

    [Service]
Restart=always
RestartSec=5

    Save and exit. systemd stores it at:

    /etc/systemd/system/nginx.service.d/override.conf

    It automatically reloads, and your change is layered on top of the original file. Check the result with systemctl cat nginx.

    🧠 Analogy: The original job description stays in the library. You clip a sticky note on top: "Also: always restart if you fall over." If you remove the sticky note, everything is back to normal.

    (sudo systemctl edit --full nginx makes a full private copy in /etc instead.)

    11. 🎉 Wants, Requires, After: the guest list vs the seating chart

    Units can depend on each other. This is where people mix up two different ideas:

    Idea Keywords Question it answers
    Dependency Wants=, Requires= "Should that other unit also be started along with me?"
    Ordering After=, Before= "In what order do we start?"

    🎂 The party analogy: Wants= is the guest list. "I'd like Priya to come to my party." After= is the seating order. "If she does come, I'll arrive after her."

    Inviting someone does not decide who arrives first, and arriving later does not invite them. You need to say both if you mean both.

    Keyword Meaning
    Wants=x Soft dependency. Start x too, but if x fails I carry on
    Requires=x Hard dependency. If x fails or stops, I stop too
    After=x Start me after x has been started
    Before=x Start me before x

    A very common real-world line:

    [Unit]
After=network.target
Wants=network-online.target

    Common targets for ordering: network.target (network stack is set up) and network-online.target (network is actually connected). A service that needs real internet should use the second.

    See the whole tree with systemctl list-dependencies nginx.

    12. 🌗 Targets: the building's "modes"

    A target is a named state of the system, a group of units that should be running together. Think of a building's modes: "night mode" (minimal lights), "business hours" (everything on).

    Target Mode
    rescue.target Emergency repair, minimal services, root shell
    multi-user.target Full system, no GUI (servers)
    graphical.target Full system plus graphical login (desktops)
    poweroff.target / reboot.target Shutting down / rebooting 
    systemctl get-default                              # what mode do we boot into?
sudo systemctl set-default multi-user.target       # boot to text mode next time
sudo systemctl set-default graphical.target        # back to GUI
sudo systemctl isolate rescue.target               # switch mode right now

    📜 For the history buffs: old Linux had runlevels (0-6). Targets are the modern equivalent: runlevel 3 ≈ multi-user.target, runlevel 5 ≈ graphical.target. Mentioned in old tutorials? Now you can translate.

    This is also the "destination" in the boot journey from the boot page. systemd's job during boot is simply to reach the default target.

    13. 📹 journalctl: the building's CCTV and logbook

    Every service's output, every kernel message, every login attempt gets collected by systemd-journald into one central, indexed log called the journal.

    journalctl is the tool that reads it.

    🆚 Old way: each program writes its own text file in /var/log (syslog, auth.log, nginx/error.log...), and you grep your way through them. Journal way: one searchable database where you can filter by service, time, severity, or boot.

    The journal is stored in binary form (that's why you can't cat it) in /var/log/journal/ (persistent) or /run/log/journal/ (gone after reboot). Ubuntu normally keeps it persistent. Traditional text logs like /var/log/syslog often still exist too.

    The commands, from the basics up

    journalctl                     # everything, oldest first (use arrow keys, q to quit)
journalctl -r                  # newest first
journalctl -n 50               # last 50 lines
journalctl -f                  # follow live, like `tail -f`

    Filter by service ⭐ (the one you'll use most)

    journalctl -u nginx            # only nginx's logs
journalctl -u nginx -f         # follow nginx live
journalctl -u nginx -n 100 --no-pager

    Filter by boot

    journalctl -b                  # this boot only
journalctl -b -1               # the previous boot (handy after a crash!)
journalctl --list-boots        # all boots the journal remembers

    Filter by time

    journalctl --since "1 hour ago"
journalctl --since "2026-10-18 09:00" --until "2026-10-18 10:00"
journalctl --since today

    Filter by severity

    journalctl -p err              # errors and worse
journalctl -p warning -b       # warnings and worse, this boot

    Priority levels, from worst to chattiest: emerg → alert → crit → err → warning → notice → info → debug.

    Kernel messages

    journalctl -k                  # same idea as `dmesg`

    The famous -xeu mystery, solved

    When a service fails, systemd tells you: "See 'journalctl -xeu nginx.service' for details." These are three flags squashed together:

    Flag Meaning
    -x Add explanatory help text to certain messages
    -e Jump to the end (newest lines)
    -u nginx.service Only this unit

    So -xeu nginx = "show me nginx's latest logs, with explanations." Not so scary now.

    Searching and combining

    journalctl -u ssh -p err --since yesterday
journalctl -b -u nginx | grep -i "permission"

    Managing the journal's size

    Journals can grow big:

    journalctl --disk-usage                 # how much space is it eating?
sudo journalctl --vacuum-time=2weeks    # delete entries older than 2 weeks
sudo journalctl --vacuum-size=500M      # trim down to 500 MB

    14. ⏰ Timers: cron's modern cousin

    Want to run something on a schedule? The classic tool is cron. systemd offers timers, with extras: logs in the journal, "run missed jobs after the PC was off", dependency handling, and easy status checks.

    A timer needs two files: the service (what to run) and the timer (when).

    /etc/systemd/system/backup.service

    [Unit]
Description=Nightly backup

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh

    /etc/systemd/system/backup.timer

    [Unit]
Description=Run backup daily

[Timer]
OnCalendar=daily
Persistent=true

[Install]
WantedBy=timers.target

    sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer     # note: enable the TIMER, not the service
systemctl list-timers                        # see all timers and when they fire next
    • OnCalendar=daily means once a day. You can also write things like OnCalendar=Mon *-*-* 09:00:00.
    • Persistent=true means "if the computer was off at the scheduled time, run it when it wakes up."
    • OnBootSec=10min means "10 minutes after boot."

    Test a calendar expression with: systemd-analyze calendar "Mon *-*-* 09:00:00".

    15. ⏱️ systemd-analyze: why is my boot slow?

    systemd-analyze                  # total boot time: firmware + loader + kernel + userspace
systemd-analyze blame            # services ranked by how long they took
systemd-analyze critical-chain   # the chain of units that actually held up boot

    blame shows who was slow, but not necessarily who delayed boot (services start in parallel). critical-chain shows the bottleneck path. Start there.

    👤 User services

    Regular users can have their own services too, without sudo:

    systemctl --user status
systemctl --user enable --now my-app

    User unit files go in ~/.config/systemd/user/. Handy for personal background tasks.

    The old service command still works

    sudo service nginx restart

    It's a legacy wrapper that quietly calls systemctl for you. If you see it in an old tutorial, it still works.

    17. 🕵️ When a service fails: the detective checklist

    Same routine, every time. Memorise this and you'll fix 90% of problems:

    1. systemctl status <service>          → what state? any hint in the last log lines?
2. journalctl -xeu <service>           → the full story, newest at the bottom
3. Fix the cause (config, path, permission...)
4. sudo systemctl daemon-reload        → ONLY if you edited the unit file
5. sudo systemctl restart <service>
6. systemctl status <service>          → green? 🎉

    Common culprits

    Message / symptom What it usually means
    Unit xyz.service not found Typo in the name, file in the wrong folder, or you forgot daemon-reload
    status=203/EXEC systemd couldn't execute ExecStart: wrong path, or the file isn't executable (chmod +x), or a missing #! first line
    status=217/USER The User= you specified doesn't exist
    status=200/CHDIR WorkingDirectory= doesn't exist
    Start request repeated too quickly It crashed several times in a row, and systemd gave up. Fix the underlying error, then sudo systemctl reset-failed <service>
    Failed to connect to bus / Access denied You forgot sudo for a system-wide action
    Job failed. See "journalctl -xe" Exactly what it says. Run it!
    Service works manually but fails under systemd systemd runs it with a minimal environment (no $PATH like your shell, different user, no terminal). Use full paths and set Environment=
    Changed config, nothing changed You didn't restart/reload. Or you edited the wrong file. Check systemctl cat

    🧠 The golden rule: status tells you that something is wrong. journalctl tells you why.

    18. 📋 Cheat Sheet

    systemctl

    I want to... Command
    See a service's state systemctl status X
    Start / stop now sudo systemctl start X / stop X
    Restart / reload config sudo systemctl restart X / reload X
    Start at every boot sudo systemctl enable X
    Both enable and start sudo systemctl enable --now X
    Stop auto-start sudo systemctl disable X
    Block a service entirely sudo systemctl mask X
    See what's failing systemctl --failed
    List all services systemctl list-units --type=service
    See the unit file(s) systemctl cat X
    Override a unit safely sudo systemctl edit X
    Re-read unit files sudo systemctl daemon-reload
    Clear a "failed" mark sudo systemctl reset-failed X
    Check/change boot mode systemctl get-default / set-default
    List timers systemctl list-timers

    journalctl

    I want to... Command
    Logs for one service journalctl -u X
    Follow live journalctl -u X -f
    Latest with explanations journalctl -xeu X
    This boot only journalctl -b
    Previous boot journalctl -b -1
    Errors only journalctl -p err
    Time range journalctl --since "1 hour ago"
    Kernel messages journalctl -k
    Check disk usage journalctl --disk-usage
    Trim old logs sudo journalctl --vacuum-time=2weeks

    The one-line mental model

    systemd = manager · unit file = job description · systemctl = walkie-talkie · journalctl = CCTV · target = building mode · enable = shortcut in the boot to-do folder · daemon-reload = "re-read the paperwork"

    🎬 Final Words

    Next time you paste sudo systemctl daemon-reload && sudo systemctl enable --now myapp, you'll know exactly what each piece does, and, more importantly, what to do when it doesn't work.
