    👥 Users & Groups in Linux: Who Are You, and What Are You Allowed to Do?

    Quick quiz. You've just joined a team, and your senior says: "I'll make an account for you on the server. Send me your username."

    A few minutes later you get this back:

    sam is not in the sudoers file. This incident will be reported.

    Dramatic, right? 😅 (Don't worry, nobody is coming to your house. The attempt is just written in a log.)

    That one line is a whole lesson: Linux is built around who you are and what you're allowed to do. In this page we'll learn how to create, inspect, change, lock, and remove users and groups, and understand what's really happening behind each command.

    ☕ Coffee time. This is one of the most important pages in the whole series.

    1. 🤔 Why Linux is obsessed with users

    Remember the history page? Unix was born in the 1960s-70s in the era of time-sharing: one big, expensive computer, many people using it at the same time from different terminals.

    That immediately raises problems:

    • How do we stop Alice from reading Bob's files?
    • How do we stop a student from deleting the whole system?
    • Who's allowed to install software or shut the machine down?

    The answer: every person (and every program) has an identity, and every file and action is checked against that identity. Linux inherited this design, which is why it's so solid for servers, and why a virus on Linux has a harder time doing system-wide damage than on a single-user-minded system.

    🧠 Even if you're the only person using your laptop, Linux is still multi-user. Your web server, your printer service, and your database all run as their own users, so that if one is compromised, it can't touch everything else.

    2. 🏢 The mental model: an apartment building with keycards

    Picture Linux as an apartment building:

    In the building In Linux
    🧑 A resident with a personal keycard A user (with a unique number called a UID)
    🏠 Their private apartment Their home directory (/home/sam)
    👥 A club or team (gym members, book club) A group (with a number called a GID)
    🔑 The master key that opens everything The root user (UID 0)
    📝 "Borrow the master key, but sign the logbook" sudo (and the log entry it leaves)
    📒 The resident register at reception /etc/passwd, /etc/shadow, /etc/group
    🏷️ The keycard office Tools like adduser, usermod, passwd

    Hold on to this picture. Every command below is just "someone at the keycard office doing paperwork."

    🔢 Key insight: Linux doesn't actually care about names. It cares about numbers. sam is a friendly label for UID 1000. Files are owned by the number, and names are just looked up for our convenience.

    3. 🎫 The three kinds of users

    Kind UID range (typical) Who is it? Can log in?
    👑 root 0 The superuser. Can do anything Possible, but normally disabled on Ubuntu
    🤖 System users 1 to 999 Accounts for services and programs: www-data (web server), syslog, daemon, nobody ❌ No (no password, shell set to nologin)
    🧑 Regular users 1000 and up Real humans like you ✅ Yes

    Why do system users exist? Least privilege. If your web server runs as www-data instead of root and gets hacked, the attacker is trapped in a tiny, powerless room instead of holding the master key.

    🎭 You saw this earlier: in the systemd page a service can be run with User=someone. Now you know who that someone is.

    The UID ranges are defined in /etc/login.defs if you're curious. (Ubuntu and Debian start regular users at 1000.)

    4. 📒 Where users live: the files behind the scenes

    When you "create a user", commands simply add lines to a few plain text files in /etc (the settings area from the file system page). Learn these and everything makes sense.

    4.1 /etc/passwd: the register of users

    cat /etc/passwd

    Each line is one user, with 7 fields separated by colons:

    sam:x:1000:1000:Sam Rai,,,:/home/sam:/bin/bash
│   │  │    │      │         │          └── 7. login shell
│   │  │    │      │         └───────────── 6. home directory
│   │  │    │      └─────────────────────── 5. full name / comment (GECOS)
│   │  │    └────────────────────────────── 4. primary group ID (GID)
│   │  └─────────────────────────────────── 3. user ID (UID)
│   └────────────────────────────────────── 2. password placeholder ("x" = look in shadow)
└────────────────────────────────────────── 1. username

    🤨 Fun fact: The file is called "passwd" because passwords used to be stored right inside it. But the file must be readable by everyone (programs need it to translate UIDs to names), so anyone could copy the password hashes. The fix was to move them to /etc/shadow, which only root can read. The name stuck, the passwords left.

    A system user line looks like:

    www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin

    Notice the shell: /usr/sbin/nologin. It politely refuses interactive logins. A door with no handle.

    4.2 /etc/shadow: the vault of password hashes

    sudo cat /etc/shadow      # root only

    sam:$y$j9T$abc...xyz:20744:0:99999:7:::
 │       │             │   │   │   └── 6. warn this many days before expiry
 │       │             │   │   └────── 5. max days before password must change
 │       │             │   └────────── 4. min days between changes
 │       │             └────────────── 3. last change (days since 1 Jan 1970)
 │       └──────────────────────────── 2. the password HASH (never the password itself!)
 └──────────────────────────────────── 1. username
    • Passwords are stored as one-way hashes, not text. Even root can't "read" your password. The system hashes what you type and compares.
    • The prefix tells the algorithm: $y$ = yescrypt (modern Ubuntu default), $6$ = SHA-512 (older), $5$ = SHA-256, $1$ = MD5 (ancient, avoid).
    • A field starting with ! or equal to * means no password login possible. ! in front of a hash means the account is locked.
    • "Days since 1 Jan 1970" is the Unix epoch. Yes, Unix time itself is a callback to the history lesson.

    4.3 /etc/group: the register of groups

    developers:x:1005:sam,priya,arjun
│          │ │    └── members (supplementary)
│          │ └─────── GID
│          └───────── password placeholder (rarely used)
└──────────────────── group name

    4.4 Other important files

    File / folder Purpose
    /etc/gshadow Protected group info (group passwords/admins), the shadow's twin for groups
    /etc/skel/ Template for new home directories. Anything here is copied into every new user's home (.bashrc, .profile...)
    /etc/login.defs System-wide defaults: UID ranges, password aging, umask
    /etc/adduser.conf Defaults for the friendly adduser command (Debian/Ubuntu)
    /etc/default/useradd Defaults for the low-level useradd command
    /etc/sudoers and /etc/sudoers.d/ Who may use sudo, and how
    /etc/shells List of valid login shells
    /home/<user> The user's personal space
    /var/log/auth.log (or journalctl) Log of logins, sudo use, failures

    🧰 Don't edit these by hand!

    Technically they're just text files. But a typo in /etc/passwd can lock everyone out. Use the proper commands (adduser, usermod...) or the safe editors (vipw, visudo). Treat these files like the reception's register: read freely, write through the front desk.

    5. 🔍 Who am I? Inspecting users

    Before changing anything, learn to look:

    whoami             # your username
id                 # your UID, GID, and ALL groups
id sam             # same, for another user
groups             # just the group names
groups sam

    A typical id output:

    uid=1000(sam) gid=1000(sam) groups=1000(sam),4(adm),27(sudo),100(users)

    Read it as: "I'm sam, UID 1000. My main group is sam. I'm also in adm, sudo and users."

    Listing users and groups

    getent passwd              # ALL users (local + network/LDAP if configured)
getent passwd sam          # one user
getent group               # all groups
getent group sudo          # who's in the sudo group?

cut -d: -f1 /etc/passwd    # just the usernames

    Only the real humans (UID 1000+)

    getent passwd | awk -F: '$3 >= 1000 && $3 < 65534 {print $1}'

    💡 getent is better than reading /etc/passwd directly because it also asks any network directories (like company LDAP). Same output format, more complete.

    6. ➕ Creating users

    Linux has two commands for this, which confuses everybody at first.

    adduser vs useradd

    adduser useradd
    Style 🤝 Friendly, interactive 🔧 Low-level, raw
    Available Debian / Ubuntu (a wrapper script) Every Linux
    Creates home dir? ✅ Yes, automatically ❌ Only if you add -m
    Asks for password? ✅ Yes ❌ No (set it afterwards with passwd)
    Default shell /bin/bash May be a basic /bin/sh unless you pass -s
    Best for Humans typing commands Scripts and automation

    🍕 Analogy: adduser is the waiter who asks "how would you like your steak?" useradd is handing the kitchen a raw ticket with only what you wrote on it. Same kitchen, different experience.

    The friendly way: adduser

    sudo adduser sam

    Adding user `sam' ...
Adding new group `sam' (1001) ...
Adding new user `sam' (1001) with group `sam' ...
Creating home directory `/home/sam' ...
Copying files from `/etc/skel' ...
New password:
Retype new password:
Full Name []: Sam Rai
Room Number []:
...

    What just happened? (the click moment 💡)

    Behind that friendly dialogue, these things occurred:

    1. A line was added to /etc/passwd (the user).
    2. A line was added to /etc/shadow (their password hash).
    3. A new group with the same name was created in /etc/group. By default every user gets a personal primary group.
    4. /home/sam was created, owned by sam.
    5. Files from /etc/skel (.bashrc, .profile...) were copied in.

    Check it yourself:

    grep sam /etc/passwd
grep sam /etc/group
ls -la /home/sam

    The precise way: useradd

    sudo useradd -m -s /bin/bash -c "Sam Rai" sam
sudo passwd sam

    Key options:

    Option Meaning
    -m Create the home directory. (Forget this and you'll have a user with no home!)
    -s /bin/bash Set the login shell
    -c "Sam Rai" Comment / full name
    -d /path Custom home directory
    -u 1500 Choose a specific UID
    -g groupname Set the primary group
    -G group1,group2 Set supplementary groups at creation
    -e 2027-12-31 Account expires on this date
    -r Create a system user (low UID, no home)

    Create and give groups in one go

    sudo useradd -m -s /bin/bash -G sudo,developers sam

    Creating a system (service) user

    For a background app that should never log in:

    sudo useradd -r -s /usr/sbin/nologin myapp
# or the friendly Debian way:
sudo adduser --system --group --no-create-home myapp

    Then in a systemd unit: User=myapp. Least privilege, achieved. 🎯

    Create a user without a password (for SSH-key-only access)

    sudo adduser --disabled-password sam

    7. 🔐 Passwords and account locking

    Setting and changing passwords

    passwd                  # change YOUR OWN password
sudo passwd sam         # set/reset sam's password (as admin)

    Root can set any password without knowing the old one. This is the standard fix for "I forgot my password" on a user account.

    Locking, unlocking, expiring

    Goal Command What happens
    🔒 Lock the account's password sudo passwd -l sam Puts a ! in front of the hash in /etc/shadow
    🔓 Unlock sudo passwd -u sam Removes the !
    ⏰ Force a new password at next login sudo passwd -e sam Expires the password immediately
    📊 Show password status sudo passwd -S sam L = locked, P = has password, NP = no password
    📅 Set account expiry date sudo usermod -e 2027-06-30 sam Account dies on that date
    🧐 View aging info sudo chage -l sam Last change, expiry, warnings
    🔁 Require change every 90 days sudo chage -M 90 sam Sets max password age

    ⚠️ Subtle point: passwd -l locks the password. The user could still log in with an SSH key, since that doesn't use the password! To truly block everything, also expire the account or change their shell:

    bash sudo usermod -e 1 sam # expire the account (date in the past) sudo usermod -s /usr/sbin/nologin sam # no interactive shell

    Quick glossary of "ways to disable someone"

    Method Blocks password login Blocks SSH key login Reversible
    passwd -l (lock) ✅ ❌ Yes
    usermod -e 1 (expire account) ✅ ✅ Yes (usermod -e "")
    Shell = nologin ✅ ✅ (no shell to run) Yes
    userdel (delete) ✅ ✅ ❌ No

    8. 🔧 Modifying existing users

    The tool is usermod: "user modify". Pattern:

    sudo usermod  <OPTIONS>  <username>

    The most-used options

    Task Command
    Add to a group (⭐ always with -a) sudo usermod -aG docker sam
    Change login shell sudo usermod -s /bin/zsh sam
    Change full-name comment sudo usermod -c "Samir Rai" sam
    Change username sudo usermod -l newname oldname
    Move home directory sudo usermod -d /new/home -m sam
    Change UID sudo usermod -u 1500 sam
    Lock / unlock sudo usermod -L sam / -U sam
    Set expiry date sudo usermod -e 2027-06-30 sam

    🚨 The most expensive typo in Linux administration

    sudo usermod -G docker sam      # ❌ REPLACES all of sam's supplementary groups!
sudo usermod -aG docker sam     # ✅ APPENDS docker to the existing list

    Forgetting the -a means sam is removed from sudo, adm, and every other group and is left only with docker. Remember it as "-a = add, don't replace", or as "-aG = add to Group."

    Renaming a user properly (full recipe)

    Changing only the login name leaves the old home folder and group behind. Do all three:

    sudo usermod -l newname oldname              # 1. change login name
sudo groupmod -n newname oldname             # 2. rename the matching group
sudo usermod -d /home/newname -m newname     # 3. rename/move the home folder

    (The user must not be logged in, or have running processes, while you do it.)

    Users can change some things themselves, with no sudo

    passwd           # own password
chsh -s /bin/zsh # own login shell
chfn             # own full name and contact info

    9. ❌ Deleting users, safely

    The commands

    sudo deluser sam                       # remove user, KEEP the home directory
sudo deluser --remove-home sam         # remove user AND home directory
sudo deluser --remove-all-files sam    # remove user and ALL files they own on the system

sudo userdel sam                       # raw version, keeps home
sudo userdel -r sam                    # raw version, removes home and mail

    (deluser is the friendly Debian/Ubuntu one; userdel is the universal low-level one.)

    Remove a user from a group (not delete the user!)

    sudo deluser sam developers        # Debian/Ubuntu friendly way
sudo gpasswd -d sam developers     # works everywhere

    🧯 The safe-offboarding routine

    Deleting is permanent. A careful admin does this instead of deleting in a hurry:

    1. Lock and disable first: bash sudo usermod -L -e 1 -s /usr/sbin/nologin sam
    2. Kick out active sessions: bash sudo pkill -KILL -u sam
    3. Back up the home directory: bash sudo tar czf /root/sam-home-backup.tar.gz /home/sam
    4. Wait (days or weeks) in case someone needs their data.
    5. Then delete: sudo deluser --remove-home sam

    🕳️ The orphan problem

    Files owned by a user keep the UID number even after the user is gone. In ls -l they show as a bare number like 1001. If a new user later gets that same UID, they would inherit those old files. Spooky and a security risk!

    Find stray files:

    sudo find / -nouser -o -nogroup 2>/dev/null

    ❗ Common error: "userdel: user sam is currently used by process 1234" means they're still logged in or running something. Kill their processes first (step 2), then retry.

    10. 👥 Groups: teams with shared keys

    Managing permissions per person gets messy fast. Groups solve this: give permissions to the group once, then just add or remove people.

    🏀 Analogy: A sports club membership. The gym's rule says "members of the Basketball Club may use Court 2." To let Priya play, you don't change the court's rules. You just add Priya to the club.

    Primary vs supplementary groups

    Every user has:

    • One primary group: used as the default group for files they create. Usually a personal group with the same name as the user (sam:sam).
    • Zero or more supplementary groups: extra memberships that grant extra access (sudo, docker, developers...).
    id sam
# uid=1000(sam) gid=1000(sam) groups=1000(sam),27(sudo),1005(developers)
#                    ▲ primary          ▲ supplementary groups

    Group commands

    Task Command
    Create a group sudo groupadd developers
    Create a system group sudo groupadd -r myapp
    Delete a group sudo groupdel developers
    Rename a group sudo groupmod -n newname oldname
    Add a user to a group sudo usermod -aG developers sam
    Same, friendly (Debian/Ubuntu) sudo adduser sam developers
    Same, via gpasswd sudo gpasswd -a sam developers
    Remove a user from a group sudo gpasswd -d sam developers
    List a user's groups groups sam
    List members of a group getent group developers
    Change a user's primary group sudo usermod -g developers sam

    ⏳ "I added myself to the group, but it doesn't work!"

    Group membership is read when you log in. Your current session still carries the old list. Fix it by either:

    • Logging out and back in (the clean fix), or
    • Starting a shell with the new group: newgrp docker, or
    • Opening a fresh login: su - sam

    This is the cause of 80% of "it still says permission denied" confusion after usermod -aG docker $USER.

    Famous groups on Ubuntu

    Group What membership gives you
    sudo Permission to use sudo (admin powers)
    adm Read access to many log files in /var/log
    docker Run Docker without sudo (⚠️ this is practically root-equivalent!)
    www-data The web server's group, which is used to share web files
    dialout Access to serial ports (Arduino, modems)
    plugdev Access to pluggable devices (USB gadgets)
    lpadmin Manage printers
    audio, video Access to sound and graphics devices
    users Generic group for ordinary users

    🗂️ A real use case: a shared project folder

    sudo groupadd developers
sudo usermod -aG developers sam
sudo usermod -aG developers priya

sudo mkdir /srv/project
sudo chgrp developers /srv/project
sudo chmod 2775 /srv/project

    Now Sam and Priya can both work in /srv/project. (That leading 2 is the setgid bit, which makes new files automatically belong to the developers group. We'll unpack the numbers on the permissions page, coming next.)

    11. 👑 root, su and sudo

    Who's root?

    root is the user with UID 0: no restrictions, no safety net, able to read, change, or delete anything. It's the master key from our building analogy.

    On Ubuntu, the root account has no usable password by default. You aren't supposed to log in as root. Instead you borrow its powers briefly with sudo.

    sudo: borrow the master key, sign the logbook

    sudo apt update                  # run ONE command as root
sudo -i                          # open a root shell (careful!)
sudo -u priya whoami             # run a command AS another user (prints: priya)
sudo -l                          # list what YOU are allowed to do with sudo
sudo !!                          # re-run your previous command with sudo (a classic)

    Why sudo is brilliant: 1. It asks for your password, not root's. (Just proof that it's really you at the keyboard.) 2. It's logged: who ran what, and when (journalctl _COMM=sudo or /var/log/auth.log). 3. It grants power one command at a time, not an all-powerful session. 4. It can be fine-tuned per user and per command.

    🥪 Fun fact: sudo stands for "superuser do" (purists say "substitute user do"). Its most famous cultural moment is the xkcd comic where "Make me a sandwich" gets refused, but "Sudo make me a sandwich" works.

    Giving someone sudo powers

    On Ubuntu, simply put the user in the sudo group:

    sudo usermod -aG sudo sam

    They must log out and in again for it to apply. Take it away with sudo gpasswd -d sam sudo.

    Fine-grained control: visudo

    The rules live in /etc/sudoers. Never edit it with a normal editor. A syntax error can lock everyone out of sudo. Use visudo, which checks syntax before saving:

    sudo visudo

    The key lines:

    root    ALL=(ALL:ALL) ALL
%sudo   ALL=(ALL:ALL) ALL

    How to read who where=(as_whom:as_which_group) what:

    Part Meaning
    %sudo The group sudo (the % means "group". Without it, it's a single user)
    ALL= On all hosts
    (ALL:ALL) May act as any user and any group
    ALL May run any command

    Examples

    # Priya may ONLY restart nginx, nothing else:
priya ALL=(root) /usr/bin/systemctl restart nginx

# The 'deploy' user can run the deploy script without a password prompt:
deploy ALL=(root) NOPASSWD: /usr/local/bin/deploy.sh

    ✅ The tidy way: drop-in files

    Instead of editing the main file, add a small file in /etc/sudoers.d/:

    sudo visudo -f /etc/sudoers.d/priya

    (Same "put your changes in your own file" idea as systemd drop-ins. 😉)

    ⚠️ NOPASSWD warning: It's convenient for automation, but it removes the safety check. Use it only for specific, narrow commands, never NOPASSWD: ALL on a machine that matters.

    su: become another user entirely

    su - priya        # become priya, with HER full environment (login shell)
su priya          # become priya, but keep much of YOUR environment
su -              # become root (needs root's password, so usually disabled on Ubuntu)

    The - (dash) means "start a fresh login shell": her home directory, her $PATH, her settings. Without it you're in a hybrid, and weird bugs appear. When in doubt, use su -.

    sudo vs su at a glance

    sudo su
    Asks for Your password Target user's password
    Scope One command (or a shell with -i) Full session as that user
    Logging Detailed per command Basic
    Modern default? ✅ Yes (Ubuntu) Rarely needed

    12. 👀 Who is logged in right now?

    who                     # who's logged in, from where
w                       # same, plus what each person is doing
users                   # just the names
last                    # history of logins (newest first)
last -n 10              # the last 10
sudo lastb              # FAILED login attempts (spotting brute-force attacks!)
loginctl list-sessions  # systemd's view of sessions

    Kick someone off

    sudo pkill -KILL -u sam            # kill all of sam's processes
sudo loginctl terminate-user sam   # end all of sam's sessions the systemd way

    Check logs for login and sudo activity

    sudo journalctl _COMM=sudo -b      # all sudo use this boot
sudo less /var/log/auth.log        # login and authentication log
journalctl -u ssh --since today    # SSH logins today

    (All callbacks to the journalctl section on the previous page.)

    13. 🍳 Real-world recipes

    Recipe 1: Onboard a new teammate with SSH-key access and sudo

    sudo adduser --disabled-password priya
sudo usermod -aG sudo,developers priya

sudo mkdir -p /home/priya/.ssh
echo "ssh-ed25519 AAAA... priya@laptop" | sudo tee /home/priya/.ssh/authorized_keys
sudo chmod 700 /home/priya/.ssh
sudo chmod 600 /home/priya/.ssh/authorized_keys
sudo chown -R priya:priya /home/priya/.ssh

    🔑 SSH is picky: if .ssh or authorized_keys are readable by others, it silently refuses the key. The 700 and 600 aren't decoration. (More on those numbers in the permissions page.)

    Note: with --disabled-password and sudo, Priya can't use sudo without a password set. Run sudo passwd priya if she'll need to, or grant a specific NOPASSWD rule.

    Recipe 2: Someone leaves the team

    sudo usermod -L -e 1 -s /usr/sbin/nologin sam
sudo pkill -KILL -u sam
sudo tar czf /root/sam-home.tar.gz /home/sam
sudo gpasswd -d sam sudo
# ...weeks later, when sure:
sudo deluser --remove-home sam

    Recipe 3: A service account for your app

    sudo adduser --system --group --no-create-home --shell /usr/sbin/nologin myapp
sudo chown -R myapp:myapp /opt/myapp
# in the systemd unit: User=myapp  Group=myapp

    Recipe 4: A user forgot their password

    sudo passwd sam                 # set a new one
sudo passwd -e sam              # (optional) force them to choose their own at next login

    Recipe 5: You lost sudo access to your own machine

    If nobody has admin rights, boot into recovery mode from the GRUB menu (the bootloader from the boot page), choose a root shell, remount the disk as writable (mount -o remount,rw /), and run usermod -aG sudo yourname. Yes, physical access is power, which is why disk encryption and BIOS/UEFI passwords exist.

    Recipe 6: Audit who has real powers

    awk -F: '$3 == 0 {print $1}' /etc/passwd     # who has UID 0? (should be ONLY "root")
getent group sudo                             # who's in sudo?
sudo grep -r NOPASSWD /etc/sudoers /etc/sudoers.d/   # any passwordless rules?

    If anything besides root shows up with UID 0, investigate immediately.

    14. 🔒 Security habits worth building

    • Never work as root. Use your normal account and sudo only when needed. Read a command twice before putting sudo in front of it.
    • Least privilege: give people only the groups and sudo rules they need.
    • Prefer SSH keys to passwords for remote access.
    • Remove or lock accounts promptly when people leave.
    • Don't share accounts. One person, one user, so logs are meaningful.
    • Treat the docker group like root. Anyone in it can effectively become root.
    • Use strong, unique passwords (or a password manager) and consider chage -M aging for shared servers.
    • Keep an eye on logs: last, lastb and journalctl tell you what's happening.

    15. 🆘 When things go wrong

    Message / symptom What it usually means Fix
    sam is not in the sudoers file. This incident will be reported. The user isn't in the sudo group sudo usermod -aG sudo sam (from an admin account), then re-login
    usermod: user sam is currently used by process 1234 They're logged in or a process runs as them sudo pkill -KILL -u sam, then retry
    adduser: The user 'sam' already exists Name taken Pick another or check getent passwd sam
    Group change "didn't work" Groups are read at login Log out/in, or newgrp groupname
    New user can't log in No password set, account locked, or shell is nologin sudo passwd sam; check sudo passwd -S sam; check shell in /etc/passwd
    User created with useradd has no home / odd prompt Forgot -m / -s /bin/bash sudo mkdir -p /home/sam && sudo chown sam:sam /home/sam and sudo usermod -s /bin/bash sam
    su: Authentication failure su - to root needs root's password, which Ubuntu leaves unset Use sudo -i instead
    Lost all groups after usermod -G Forgot -a Re-add them with usermod -aG ...
    SSH key ignored Wrong permissions on ~/.ssh or authorized_keys chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys
    Files show a number instead of an owner Their user was deleted (orphaned UID) Find with find / -nouser, reassign with chown
    Locked out after editing sudoers Edited without visudo Boot recovery mode and fix the file (and use visudo next time!)

    16. 📋 Cheat Sheet

    Inspect

    Task Command
    Who am I? whoami · id
    My groups groups
    All users / one user getent passwd · getent passwd sam
    Group members getent group developers
    Who's logged in? who · w
    Login history / failures last · sudo lastb
    Password status sudo passwd -S sam

    Create / change / remove users

    Task Command
    New user (friendly) sudo adduser sam
    New user (script style) sudo useradd -m -s /bin/bash sam
    Set password sudo passwd sam
    Add to group ⭐ sudo usermod -aG groupname sam
    Change shell sudo usermod -s /bin/zsh sam
    Rename user sudo usermod -l new old
    Lock / unlock sudo usermod -L sam / -U sam
    Expire account sudo usermod -e 2027-06-30 sam
    Delete (keep files) sudo deluser sam
    Delete + home sudo deluser --remove-home sam

    Groups

    Task Command
    Create / delete sudo groupadd name · sudo groupdel name
    Add / remove member sudo gpasswd -a sam grp · sudo gpasswd -d sam grp
    Use new group now newgrp grp

    Privilege

    Task Command
    Run one command as root sudo command
    Root shell sudo -i
    Be another user su - priya
    What can I sudo? sudo -l
    Edit sudo rules safely sudo visudo · sudo visudo -f /etc/sudoers.d/name

    🧠 The one-line mental model

    User = keycard (a UID) · group = club membership (a GID) · root = master key (UID 0) · sudo = borrow the master key and sign the logbook · /etc/passwd, shadow, group = the reception registers · usermod -aG = add to a club, don't replace the whole membership list

    🎬 Final Words

    Next time you type sudo usermod -aG docker $USER, you'll know precisely what's happening: you're asking the keycard office to add you to the docker club, an update to /etc/group that your session will only notice after you log in again.

    Users and groups are the foundation of Linux security, and also the foundation of the next topic: file permissions, where all those rwx letters and numbers like 755 finally make sense. Now that you know who everyone is, we can talk about what they're allowed to touch.
