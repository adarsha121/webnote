    ⚡ From Power Button to Desktop: How Linux Boots (and How It's Built)

    You press a button. A few seconds later, a polished desktop is staring back at you. It feels instant, almost boring.

    But in those few seconds, your computer performs a relay race with at least six runners, each one waking up the next, each one smarter than the last. And the very first runner wakes up believing it's 1978.

    In this page we'll follow the whole journey, from electricity to your desktop window, and then peek inside the machine to see how Linux is actually built. If the history page was where Linux came from, this one is what Linux does the moment you wake it up.

    ☕ Grab your coffee again. This one's a short trip, but a fun one.

    1. 🎭 The Big Picture: a theatre show

    Think of booting as putting on a theatre show:

    Theatre Computer
    ⚡ Power to the building Power supply feeds the hardware
    🔦 Stage crew switches on lights and checks the stage Firmware (BIOS/UEFI) tests and wakes the hardware
    📋 Stage manager finds the script and the director Bootloader (GRUB) finds and loads the kernel
    🎬 The director takes charge Kernel controls the hardware and memory
    🧰 A box of props for the first scene initramfs gets the real disk ready
    📣 Assistant directors calling the actors systemd starts services
    🎟️ Ticket counter Login screen
    🎉 The show Your desktop

    Each stage does one job, then hands the baton to the next. If any runner trips, the show doesn't start, which is why a broken bootloader gives you a scary black screen while a broken wallpaper app doesn't.

    2. 🔌 Stage 0: Electricity wakes the hardware

    You press the power button. This isn't software yet. It's pure electronics:

    1. The power supply starts up and, once its voltages are stable, sends a "power good" signal to the motherboard.
    2. Until that signal arrives, the CPU is held in reset, like an alarm clock with the snooze pressed.
    3. Once released, the CPU does something very simple: it jumps to a fixed, hard-wired memory address and runs whatever instructions it finds there.

    And what sits at that address? A small chip on your motherboard storing the firmware.

    🕰️ Fun fact: An x86 CPU wakes up in a primitive 16-bit mode, called real mode, which dates back to the 8086 chip of 1978. Even your shiny modern 64-bit processor starts the day pretending to be a 1970s relic, then quickly "grows up" through different modes as software takes over. Every PC essentially goes through a tiny evolution montage on every boot.

    3. 🔦 Stage 1: Firmware (BIOS or UEFI)

    The firmware is the first software that runs. Its jobs:

    • POST (Power-On Self-Test): "Is there RAM? Is the keyboard there? Is the CPU okay?" (That's the single beep some PCs make.)
    • Initialise basic hardware: memory controller, storage controllers, display.
    • Find something to boot from: a disk, USB stick or network.
    • Hand over control to the next stage.

    There are two generations.

    🦖 BIOS (the old guard)

    BIOS stands for Basic Input/Output System. It debuted on the original IBM PC in 1981, the same machine from our history page that launched with MS-DOS. (Fun detail: the term "BIOS" first appeared in the CP/M operating system, remember the QDOS and CP/M story?)

    How it boots: 1. Looks at the boot disk's very first 512 bytes, called the MBR (Master Boot Record). 2. Those 512 bytes hold a tiny bit of code, a partition table, and a magic signature. 3. BIOS runs that tiny code and hopes for the best.

    Yes, the entire first handover is 512 bytes, smaller than this paragraph.

    🚀 UEFI (the modern way)

    UEFI (Unified Extensible Firmware Interface) replaced BIOS on most computers from around the 2010s. It is smarter, faster, and has a graphical interface.

    • Uses a GPT partition scheme (no more tiny MBR limits).
    • Reads a special small partition called the EFI System Partition (ESP), formatted as FAT32, and runs a .efi program from it. On Ubuntu this is mounted at /boot/efi (a nice callback to the file system page).
    • Supports Secure Boot: only digitally signed bootloaders are allowed to run, to block malicious code from sneaking in before the OS wakes up. Ubuntu works with Secure Boot using a small signed helper called shim.

    BIOS vs UEFI at a glance

    BIOS (legacy) UEFI (modern)
    Born 1981 2000s era, standardised later
    Partition style MBR GPT (and supports MBR)
    Boot file First 512 bytes of the disk .efi file on the ESP
    Interface Blue text screens Can be graphical, mouse support
    Secure Boot ❌ ✅
    Speed Slower Faster

    🔎 Check which one you have: ls /sys/firmware/efi. If that folder exists, you booted with UEFI.

    4. 📋 Stage 2: The bootloader (GRUB)

    The firmware knows how to find a program on the disk, but it's far too simple to load an entire operating system. So it loads a bootloader.

    On most Linux systems, that's GRUB (GRand Unified Bootloader). And here's a fun callback: GRUB is a GNU project. Stallman's rebellion from the history page is literally what starts your computer. 🎩

    What GRUB does

    1. Shows the boot menu (the one that appears if you hold Shift on BIOS systems or tap Esc on UEFI systems during start-up in Ubuntu). This is how dual-boot works: Linux and Windows in one list.
    2. Loads the kernel and the initramfs from /boot into memory.
    3. Passes the kernel a command line with options (which disk holds the root filesystem, whether to show the splash screen, etc.).
    4. Jumps to the kernel and gets out of the way.

    You can see the options GRUB passed:

    cat /proc/cmdline

    The files it loaded live in /boot, as described in the file system page:

    /boot
├── vmlinuz-<version>      ← the compressed Linux kernel
├── initrd.img-<version>   ← the initial RAM filesystem
└── grub/grub.cfg          ← GRUB's menu and settings

    🧠 Why "vmlinuz"? "linux" is the name, "vm" originally hinted at virtual memory, and the trailing z means it's compressed. The kernel is a self-extracting archive.

    5. 🎬 Stage 3: The kernel takes over

    Now the star arrives: the Linux kernel, the very thing Linus started in 1991.

    The kernel immediately:

    1. Decompresses itself into memory.
    2. Sets up memory management (who gets which chunk of RAM).
    3. Initialises the CPU features, interrupts and timers.
    4. Detects hardware and loads the right drivers.
    5. Mounts a temporary filesystem (the initramfs, next stage).
    6. Finally starts the first user program.

    All the messages it prints along the way are recorded, and you can read them any time:

    dmesg | less

    That's the kernel's diary of its own boot, where it grumbles about hardware, announces what it found and sometimes complains about firmware bugs.

    💥 Meet the kernel panic: if something goes badly wrong in the kernel and it can't continue safely, it stops everything and prints a kernel panic message. It's Linux's cousin of the Windows blue screen, only more dramatic about the vocabulary.

    6. 🧰 Stage 4: initramfs, the tiny helper

    Here's a classic chicken-and-egg problem.

    The kernel needs drivers to read your disk. The drivers are stored on the disk. 🤯

    Solution: the initramfs (initial RAM filesystem). It's a small temporary filesystem loaded into memory by GRUB alongside the kernel. It contains just enough tools and drivers to:

    • Load the right drivers (for your NVMe, RAID, encrypted disk, etc.).
    • Ask for your disk-encryption password, if you set one up.
    • Find and mount the real root filesystem (/).
    • Switch over to the real root and start the real init system.

    Think of it as the starter pack for the first scene: a small box of props to get the stage ready, thrown away once the real set is in place.

    7. 📣 Stage 5: systemd, PID 1

    With the real root filesystem mounted, the kernel launches the very first process, the one with PID 1. On modern Ubuntu, that's systemd.

    ps -p 1
ls -l /sbin/init
# /sbin/init -> ../lib/systemd/systemd   (or similar)

    (Notice the symlinks, which tie back to the usr-merge story in the file system page.)

    Why PID 1 is a big deal

    • It's the ancestor of every other process. Every program on the system descends from it. Run pstree to see the family tree. 🌳
    • If a process loses its parent, PID 1 adopts it. It's a very patient parent.
    • If PID 1 dies, the system goes down.

    What systemd does

    1. Reads configuration from /etc/systemd and unit files from /lib/systemd and friends.
    2. Mounts disks listed in /etc/fstab.
    3. Sets up /run, /dev, /proc and /sys (the virtual filesystems).
    4. Starts services (network, sound, Bluetooth, printing, SSH...) in parallel, which is why modern boots are fast.
    5. Reaches a target, a goal state.

    Targets: boot "destinations"

    Target Meaning
    rescue.target Minimal single-user repair mode
    multi-user.target Full system, text-only (typical for servers)
    graphical.target Full system plus graphical login (typical for desktops) 
    systemctl get-default          # what target do we boot to?
systemd-analyze                # how long did the boot take?
systemd-analyze blame          # which services were slowest?
journalctl -b                  # logs from this boot

    📜 A bit of history: Before systemd, Linux distros used an older init system called SysV init, which started services one after another in scripts. Then came Upstart (Ubuntu's own attempt) and finally systemd, which became the standard across most major distros in the mid-2010s. Not everyone loves it, and the debate is a rite of passage for Linux nerds.

    8. 🎟️ Stage 6: Login screen to desktop window

    The system is up. Now the part you see.

    Step 1: The display manager

    systemd starts a display manager, the graphical login screen. On Ubuntu it's GDM. It shows your name, takes your password, and checks it using the system's authentication machinery (the account info lives in /etc/passwd and /etc/shadow, as covered earlier).

    Step 2: Your session begins

    If your password is right, the system: - Starts a session just for you. - Sets your environment, with your files and settings coming from /home/you. - Launches your desktop environment.

    Step 3: The display server and compositor

    Windows need something to draw them on screen.

    • X11 / Xorg: the old veteran, born at MIT in the 1980s, around the same time as GNU.
    • Wayland: the modern replacement, simpler and more secure. Recent Ubuntu versions use it by default.

    A compositor takes every app's window, stacks them, adds shadows and animations, and sends the final picture to your monitor.

    Step 4: The desktop environment

    This is the face of Linux, the panel, the menus, the file manager, the settings app:

    Desktop environment Vibe
    GNOME Clean, modern, Ubuntu's default
    KDE Plasma Highly customisable, Windows-like feel
    Xfce Lightweight, great for older machines
    Cinnamon / MATE Traditional, familiar layouts

    You can find out what you're running:

    echo $XDG_SESSION_TYPE      # wayland or x11
echo $XDG_CURRENT_DESKTOP   # GNOME, KDE, XFCE...

    💡 Linux superpower: the desktop is just another program. You can swap GNOME for KDE without reinstalling your system. In Windows, the desktop is glued in. In Linux, it's a replaceable layer.

    🎉 And there it is: your first window opens. From electricity to pixels.

    9. 🍰 How Linux is built: the layer cake

    Now that you've seen the boot, let's zoom out and look at the whole structure of a Linux system, as layers:

    ┌──────────────────────────────────────────────┐
│  🖥️  Applications: browser, editor, games    │
├──────────────────────────────────────────────┤
│  🪟  Desktop environment / Shell (CLI)        │
├──────────────────────────────────────────────┤
│  📚  Libraries (glibc, GTK, Qt...)            │
├════════════ system call boundary ════════════┤
│  ⚙️  KERNEL: processes, memory, files,       │
│      drivers, networking, security           │
├──────────────────────────────────────────────┤
│  🔩  Hardware: CPU, RAM, disks, devices       │
└──────────────────────────────────────────────┘
        ▲ User space above  ·  Kernel space below ▼

    🍽️ The restaurant analogy

    Restaurant Linux
    Customers Applications and you
    Menu / ordering counter Shell and desktop
    Waiter System calls
    Kitchen (the one that actually cooks) Kernel
    Stoves, fridges, ovens Hardware

    Customers never walk into the kitchen. They place an order, the waiter carries it, the kitchen does the work. Same idea.

    What the kernel actually manages

    Job What it means
    Process management Decides who runs on the CPU and for how long
    Memory management Gives each program its own safe slice of RAM
    File systems Turns raw disk blocks into files and folders
    Device drivers Talks to the hardware (exposed as files in /dev)
    Networking Handles packets, sockets and protocols
    Security Permissions, users, isolation

    🧩 Monolithic... but modular

    Remember the Tanenbaum–Torvalds debate from the history page? It was about kernel design. Tanenbaum favoured a microkernel (a tiny core with everything else separate). Linux is monolithic (the big stuff lives inside the kernel for speed).

    But Linux has a clever trick: loadable kernel modules. Drivers can be plugged in and out while the system runs, without rebooting. They live in /lib/modules/<version>/.

    lsmod              # list loaded modules
uname -r           # kernel version

    10. 🛡️ Kernel space vs user space

    The CPU has privilege levels. Linux uses two:

    • Kernel space: full power. Can touch any memory, any hardware.
    • User space: restricted. Programs get their own private memory and cannot touch hardware directly.

    🏠 Why this matters: if your browser crashes, only the browser dies. The system keeps running. It's like a kitchen fire inside one fireproof cubicle instead of the whole building. Only a bug in the kernel itself can take everything down (hello, kernel panic).

    This separation is also why Linux is famously stable and secure, and why servers can run for months or even years without a reboot.

    11. 🛎️ System calls: how apps ask the kernel for help

    Apps can't touch hardware, so how does a program read a file? It makes a system call (syscall), a formal request to the kernel.

    Common ones:

    Syscall What it asks
    open "Please open this file for me"
    read / write "Give me / save this data"
    fork / execve "Create a new process / run this program"
    mmap "Give me some memory"
    socket "Open a network connection"

    You can actually watch them happen. Install the tool with sudo apt install strace, then:

    strace ls 2>&1 | head -20

    You'll see the humble ls command making dozens of requests to the kernel just to list a folder. It's eye-opening the first time.

    🔁 Remember "everything is a file"? This is why it works. The kernel presents disks, devices, even process info (/proc) through the same open/read/write calls. One simple interface for everything.

    12. 🐚 The shell

    The shell is a program that reads what you type, interprets it, and asks the kernel (through other programs) to carry it out. It's the outer shell around the kernel's nut, hence the name. 🥜

    • The most common one is bash (the Bourne Again Shell, a pun on an older shell and a GNU project, of course).
    • Others: zsh, fish, dash.

    When you type ls, the shell searches the folders in $PATH, finds /usr/bin/ls, asks the kernel to run it, and shows you the output.

    Shell ≠ terminal. The terminal is just the window. The shell is the program running inside it.

    13. 🔍 Peek behind the curtain: commands to try

    A small tour of your own machine's boot, stage by stage:

    # Firmware: BIOS or UEFI?
ls /sys/firmware/efi

# Bootloader: what options did GRUB give the kernel?
cat /proc/cmdline

# Kernel files and version
ls /boot
uname -r

# Kernel's boot diary
dmesg | less

# PID 1 and the process family tree
ps -p 1
pstree | head -20

# systemd: boot target, timing, and slow services
systemctl get-default
systemd-analyze
systemd-analyze blame | head

# Logs from this boot
journalctl -b | less

# Desktop session
echo $XDG_SESSION_TYPE
echo $XDG_CURRENT_DESKTOP

# Kernel modules (drivers) loaded
lsmod | head

    14. 🗺️ The whole journey on one page

    # Stage Who's in charge Where it lives Job
    0 Power on Hardware Motherboard Stabilise power, release the CPU
    1 Firmware BIOS / UEFI Flash chip on the motherboard Self-test, find a boot device
    2 Bootloader GRUB /boot/grub, ESP Load the kernel and initramfs
    3 Kernel Linux /boot/vmlinuz-* Take control of hardware and memory
    4 initramfs Temporary mini-OS /boot/initrd.img-* Prepare and mount the real root
    5 Init system systemd (PID 1) /lib/systemd, /etc/systemd Start services, reach the target
    6 Login GDM Display manager Authenticate you
    7 Desktop GNOME (or other) Your session Draw your windows 🎉

    One-line version: Power → Firmware → Bootloader → Kernel → initramfs → systemd → Login → Desktop.

    🎬 Final Words

    Next time your computer boots, spare a thought for that relay race: from a CPU waking up in 1978 mode, through a 512-byte note in a boot sector, a GNU bootloader, Linus's kernel, a tiny disposable helper, and a patient PID 1, all the way to your wallpaper.

    It takes a few seconds. It's been 50 years in the making. 😉

    You don't need to memorise all the stages (unless you're preparing for an exam or a Linux job interview, where this question is a classic). This page will always be here when you need it.
